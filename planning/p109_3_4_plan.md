# P109.3 + P109.4 Plan: Bridge QMD Growth Increment Response to MKRF

## Objective

Port the K3Z-proven CT diameter response and QMD surface emission to the MKRF instance, so MKRF carries the same `feature.QMD.managed.<au_token>` standing-stock signal and `product.QMD.managed.<au_token>.<treatment>` harvested-stem numerator surfaces that K3Z already exposes.

## Current State (verified 2026-07-31)

### Core FEMIC (`src/femic/fmg/patchworks.py`)

- `_build_qmd_curve_points()` (L2275) accepts `response_age`, `response_fraction`, `response_years` and applies:
  ```python
  if response_age is not None and age >= float(response_age) and response_fraction > 0.0:
      ramp = min(1.0, max(0.0, (age - float(response_age)) / float(response_years)))
      qmd *= 1.0 + (response_fraction * ramp)
  ```
- `_resolve_commercial_thinning_config_for_au()` (L2090) reads `qmd_response_fraction` from the CT payload with default `0.10`.
- `_resolve_fertilization_config_for_au()` (L2580) reads `qmd_response_fraction_by_au` per AU with default equal to `growth_speedup_fraction_by_au`.
- The CT path uses the **flat** `qmd_response_fraction` (no per-AU override).
- The fert path uses the **per-AU** `qmd_response_fraction_by_au` (with per-AU override via `field="qmd_response_fraction"`).
- Both emit `feature.QMD.managed.<au_token>` standing-stock curves.
- Both emit `product.QMDNumerator.managed.<au_token>.<treatment>` and `product.Treated.managed.<au_token>.<treatment>` when `qmd_harvested_product_accounts_enabled=True`.

## Gap Analysis

### What's missing in MKRF

1. **QMD config block**: `qmd: enabled: true, harvested_product_accounts_enabled: true` is absent.
2. **CT `qmd_response_fraction`**: Not set in `commercial_thinning` block; core default is `0.10` but MKRF has no per-bucket or per-intensity override.
3. **QMD curve emission**: `initialize_mkrf_runtime_package()` never calls `_build_qmd_curve_points`.
4. **QMD product numerators**: No `product.QMDNumerator.managed.*` or `product.Treated.managed.*` attributes written.
5. **QMD ratio accounts**: No `scripts/targets/qmdRatioAccounts.bsh` equivalent.
6. **Pin file**: `analysis/base.pin` doesn't reference QMD targets.

### What's different about MKRF vs K3Z

1. **AU identifiers**: K3Z uses numeric AU ids (`985501001`); MKRF uses string AU ids (`cwh_dm_x_cw_hw`).
2. **Bucket structure**: K3Z uses a single CT age per AU; MKRF uses 3 age buckets (CT35/40/45) with intensity variants.
3. **Builder path**: K3Z uses the standard exporter that consumes `silviculture.*.yaml`; MKRF builds XML directly via `et.SubElement` in `mkrf.py`.
4. **No per-AU QMD override in core CT path**: The core CT `_resolve_commercial_thinning_config_for_au()` reads `qmd_response_fraction` as a flat value. MKRF needs per-bucket or per-intensity control.

## Plan

### Phase A: Core CT path per-bucket override (P109.4a)

**Goal**: Extend the core CT `_resolve_commercial_thinning_config_for_au()` to accept a per-bucket `qmd_response_fraction_by_bucket` dict, falling back to the flat `qmd_response_fraction` default.

**Why**: MKRF's 3 age buckets (CT35/40/45) need different response fractions. K3Z uses per-AU, but MKRF's structure is bucket-anchored.

**Changes**:
- `src/femic/fmg/patchworks.py`:
  - In `_resolve_commercial_thinning_config_for_au()`, after reading `qmd_response_fraction`, check for `qmd_response_fraction_by_bucket` in the payload.
  - If present and the current bucket label is in the dict, use that value; otherwise fall back to the flat value.
  - Pass the resolved value through to the config dict.

### Phase E: QMD ratio accounts script (P109.3d)

**Goal**: Add `scripts/targets/qmdRatioAccounts.bsh` to compute the ratio.

**Changes**:
- `external/femic-mkrf-instance/models/mkrf_patchworks_model/scripts/targets/qmdRatioAccounts.bsh`:
  ```bsh
  /*************************************************************
   *
   * Configure harvested-stem mean-QMD ratio accounts.
   *
   * - Numerator rows come from product.QMDNumerator.managed.*
   * - Denominator rows come from product.Treated.managed.*
   * - User-facing ratio rows are published as product.QMD.managed.*
   *
   *************************************************************/
  
  setupHarvestedQmdRatioAccounts(control, String tracksPathPrefix) {
     TreeSet numeratorAccounts = _collectAccounts(
        "product.QMDNumerator.managed.", tracksPathPrefix
     );
     TreeSet denominatorAccounts = _collectAccounts(
        "product.Treated.managed.", tracksPathPrefix
     );
  
     int configured = 0;
     for (Iterator it = numeratorAccounts.iterator(); it.hasNext();) {
        String numerator = (String)it.next();
        String suffix = numerator.substring("product.QMDNumerator.managed.".length());
        String denominator = "product.Treated.managed."+suffix;
        String ratio = "product.QMD.managed."+suffix;
        if (!denominatorAccounts.contains(denominator)) {
           throw new IllegalStateException(
              "Missing harvested-QMD denominator account for "+numerator+
              ": expected "+denominator
           );
        }
        control.addRatioAccount(ratio, numerator, denominator, 1);
        configured += 1;
     }
  
     print("Configured harvested QMD ratio accounts: "+configured);
  }
  ```
- This is identical to the K3Z version (commit `ffb1ce5`).

**Verification**:

## Open Decisions

1. **QMD response fraction values**: Placeholders (0.10/0.12/0.15) for CT35/40/45. Calibration will follow.
2. **Height/TPH support inputs**: MKRF's `managed_curves_csv` may not carry height/TPH columns. If absent, QMD will fall back to the `direct_diameter_curve_points` or `basal_area_curve_points` paths.
3. **Per-AU vs per-bucket**: MKRF uses per-bucket (CT35/40/45). K3Z uses per-AU. The core CT path needs the per-bucket extension.
